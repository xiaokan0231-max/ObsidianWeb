# 公司总览与契合评价

公司画像用于了解当前公司与岗位，并以相同维度比较最多三项。六维图表达**有依据的面试前判断**：对照已读的当前求人、公开资料与本人已确认的经历和方向，不把企业内部实际情况说成完全确认。它不是录用概率、公司综合质量或应募投入优先级。程序契约以 `lib/company-overview.ts` 为准；写入后运行 `npm run vault:verify` 并回读页面。

## 资料归属与更新

- 公司卷宗 `type: company` 的可选 `company_profile` 保存业务、人数、成立、集团／上市关系与外部口碑。公司规模、薪资、知名度都不直接换算契合分。
- 公司卷宗的可选 `company_summary` 双链指向独立 `report_kind: company-summary` 报告，同公司不同岗位共享公司层面的研究。总结不塞进 `fit_assessment.summary`；后者继续表达本人和具体岗位的一句话契合判断。
- 岗位／面谈条件保存在契合报告的 `context_facts`，不写到共享公司事实。与 job-case 的当前事实冲突时先核对原文，不自动采纳旧评分卡的值。
- 每次实质重评新建 `80_AI分析/YYYY-MM-DD_Codex_<案件或面谈短名>_会社契合.md`；不要覆盖旧报告或别的作者的分析。同日已存在则增加修订后缀。
- 新评价使用 `schema_version: 1`、`criteria_version: 2`。前者是存储结构，后者是评价口径，不要同步改成 2。旧 `criteria_version: 1` 报告保留原文、分数与旧轴；不能改版本号或把旧分数映射到新轴。按新版实质重评后再更新最新引用。
- 在真实 job-case 或面谈 TODO 上写 `company_dossier` 和 `fit_assessment` 双链，指向卷宗及最新报告。报告 `case`／`meeting` 二选一，对应同一记录；不按显示公司名合并、不为显示画像伪造案件。
- 页面显示最新画像日期，与历史准备正文分开。不要改旧准备稿来加入画像，也不要增加其轮次或第六章。

## 公司总结：从资料形成整体理解

公司总览最前面展示「公司总结」，正文完整可读，随后保留事实卡、契合画像与外部评价。用约 600～1000 字、4～6 个自然段的中文文章作为通常篇幅，依证据调整，不凑字数或硬截断。先说明这是一家怎样的公司，再展开近年变化与当前阶段，最后落到人才需求及面谈应核实的关键问题。不要把事实卡改写成列表、公司沿革流水账或新闻标题合集。

研究时至少检查以下方向，记录实际读到的资料；没有公开信息就明示缺口，不强凑数量：

- 当前业务、客户与收入模式、规模和行业位置。人数与收入分清单体／集团、正式员工／合作人员、统计时间；公司较新时从成立起回顾，不编造三到五年的历史。
- 近三到五年有依据的业务变化，以及近期约六到十二个月的新闻、公告、产品发布、客户案例、合作、收购、组织调整或财报。逐一核对发表日与事件日，旧文章新抓取不等于新事件。
- 技术博客、技术分享、经营者文章和员工访谈。优先读与业务转向、工程瓶颈、开发方式和组织建设有关的原文。区分作者、部门、时间、观点、实验和已投入生产的实践；公司自述不能视为独立口碑。
- 当前岗位的公开要求及企业明确说明的招聘背景。岗位原文使用本人登录会话；复用已核验的 vault 证据时保留其读取日期，不冒充本轮新核实。

把资料连接成「发生了什么变化 → 带来什么业务或技术任务 → 为什么可能需要这一类人」的解释。只有企业明说，才写成确定的招聘原因；根据新闻、博客与岗位交叉推出的解释写“据此判断”“可能对应”，并说明还需要确认的事项。不得由招聘多、人员增加、融资或发布新产品就断言营收增长、盈利改善或岗位是扩招；补员、替换、储备招聘未获证实时保持未知。允许“收入增长但利润承压”“集团扩张而部门情况不明”等有层次的判断；缺少连续数据时不强判上升或下降。

关键事实和判断就近附直接链接。段落可用少量加粗与行内出处，读者应能顺着文章读下去；长链接标题、阅读范围和具体限制放到报告的「资料与边界」节。网页实际全文可读才能称已读，搜索摘要仅用于发现来源。近期变化可能推翻旧卷宗时先核对差异，保留原有证据，不偷偷改写历史。

每次实质更新新建 `80_AI分析/YYYY-MM-DD_Codex_<公司短名>_公司总结.md`，同日重名加修订后缀；新报告反向关联同一个公司卷宗，再替换卷宗的 `company_summary` 引用。日期为本次资料核对时点，覆盖期间另写；来源日期及适用范围不相同时在正文说明。报告格式：

```yaml
type: ai-report
report_kind: company-summary
schema_version: 1
assessed_on: 'YYYY-MM-DD'
ai_author: Codex
company_dossier: '[[20_求職/测试/_公司]]'
coverage_period: '<实际可核验的历史区间与近期动态截止日>'
sources:
  - label: '<来源标题与发表日／统计时点>'
    url: https://example.com/news/article
  - label: '<本轮实际使用的既有证据与核验日期>'
    wiki: '[[20_求職/测试/既有证据]]'
```

正文保留一个 `## 公司总结`，下方写连续自然段，可用 Markdown 直接链接与双链；一个 `## 资料与边界` 记录各来源的实际直链、发表／事件／统计日期、阅读日期、阅读范围与支持的结论。Web 只投影「公司总结」，来源区可展开并进入完整报告。缺失总结显示待补齐；坏引用只影响总结，不应使已有公司事实与契合画像消失。

## 事实与外部评价

每项事实保存 `id/label/value/as_of/scope/sources`。人数需区分单体／集团、员工／合作人员及统计时点；有冲突时保留口径并解释，不取全文中第一个数字。没有资料的内容明确写未披露／待确认，不推断稳定性或上市状态。

外部口碑分别记录平台、原始量尺、评分、样本数、评论时段、岗位覆盖和阅读日期；不同平台不平均。评论仅是样本，不证明公司普遍情况，无法读到正文时不从搜索摘要编造正负主题。官方员工访谈属于公司自述，不能当独立口碑。

`status` 为 `available / not_researched / no_samples / restricted`，分别代表已取得可用内容、未调查、调查后未找到可用样本、访问范围受限。受限页面若有可见评分与数量可记录，但 `limitations` 必须说明只读到的范围；不为取得口碑自动登录、投稿或付费。

```yaml
company_profile:
  version: 1
  updated_on: 'YYYY-MM-DD'
  facts:
    - id: employees
      label: 员工规模
      value: '<官网数字及必要口径说明>'
      as_of: '<统计时点；未标时点则明确说明>'
      scope: '<单体／集团等>'
      sources:
        - label: 公司概要
          url: https://example.com/company
  reviews:
    - platform: '<平台名>'
      url: https://example.com/reviews
      status: restricted
      score: null
      scale: null
      sample_count: null
      comment_period: 未取得
      coverage: 未取得
      positive: []
      negative: []
      read_on: 'YYYY-MM-DD'
      limitations: '<实际可读范围>'
```

常用公司事实 id：`business/employees/founded/ownership`；岗位事实 id：`role/salary/location/work_style`。未知不填假数字；使用相同 id 才能在比较表中对齐。

## 六维评价（criteria_version: 2）

固定顺序与含义。所有判断均以面试前可取得的证据为范围：

| key | 维度 | 证据要回答的问题 |
|---|---|---|
| technical | 技术匹配 | 求人中明确的技术需求，与本人已证明的技术基础及可迁移能力是否匹配？ |
| experience | 经验发挥 | 岗位要解决的问题、交付的成果物和承担的责任，能否发挥本人已有实绩？ |
| business | 业务方向 | 公司解决的问题是否与本人当前兴趣与方向一致？ |
| role | 职责方向 | 求人声明的角色与责任方向，是否符合本人当前志向？ |
| growth | 成长方向 | 公开的具体职责或技术学习机会，是否有助于本人希望积累的经验与能力？ |
| practical | 已知条件 | 已公布的雇用、地点、工作方式、工时，与本人已确认接受的范围是否相容？ |

- **技术匹配与经验发挥分开看**：前者看技术基础和实际差距，后者看解决问题、交付和责任经历。产品名称不完全一致不自动扣分；也不能把可迁移能力写成目标产品的生产经验。
- **业务方向**按公司实际解决的问题与本人当前方向判断，不能自行用行业、规模或知名度设偏好。
- **职责方向**评价求人所声明的角色。实际决策权、配属、第一阶段责任和是否能兑现，留到面谈确认，不把招聘文案升级为已获授权。
- **成长方向**必须落到具体技术、任务或责任积累。它不证明公司提供培训、导师、晋升或一定能配属到理想项目。
- **已知条件**只评价已公开且能与本人现行接受范围对照的条件；不表示就职手续与全部待遇已成立。薪资仍在事实卡独立展示，不能把高薪、完全远程或大公司自动换成高分，也不将本人已接受的出社、地域列成缺点。

分档：1 明确不合、2 契合较弱、3 基本适配、4 明显契合、5 高度契合。已知但好坏并存可以是 3；证据不足必须是 `null`，不能先填中间分。公司业务或岗位有多个方向时，不把其中最理想方向当已配属。5 需要直接、具体的适配证据；不能因为企业自称重视成长就打高分。

每个数值必须同时有简短判断和证据：公司／岗位来源加相关本人素材。轴本身所需的公开证据不足时用 `null`，页面显示「资料不足」，在 `rationale` 和 `unknowns` 说明缺少什么；不能为了画满雷达图补分。薪资按本人现行方针协商，不自设下限。不要读取旧 `rating/fit_score_100` 作为默认值。

**面谈才能回答的问题单独进入 `fit_assessment.questions`**：例如实际裁量、具体配属、沟通分工、初期支持、在留手续支持和条件兑现。它们仍须在主图旁可见，但不因这类内部情况尚未确认就把已有公开依据的轴置为 null。`unknowns` 用于记录该轴证据的具体限制；不要把面谈问题机械复制到每一轴。公开资料若已显示明确不适配，应如实判断，不以「面谈再问」掩盖现有反证。

```yaml
type: ai-report
report_kind: company-fit
schema_version: 1
criteria_version: 2
assessed_on: 'YYYY-MM-DD'
ai_author: Codex
case: '[[20_求職/テスト/案件]]' # 无案件时改为 meeting，指向真实面谈 TODO
company_dossier: '[[20_求職/テスト/_テスト]]'
fit_assessment:
  summary: '<基于面试前资料的一句话判断，说明机会与证据范围>'
  strengths: ['<有证据的契合点>']
  questions: ['<面谈确认：实际配属、裁量或初期支持等>']
  dimensions:
    technical:
      score: 4
      rationale: '<基于公开技术需求与本人实际技术基础的判断，并说明已知差距>'
      evidence:
        - label: 当前岗位
          url: https://example.com/job
        - label: 本人技术基础
          wiki: '[[10_关于我/技術スタック#具体小节]]'
      unknowns: []
    # experience/business/role/growth/practical 也必须逐项填写。
    # 该轴公开资料不足时使用 score: null，并填写 rationale 与 unknowns。
  context_facts: [] # 每项与 company_profile.facts 使用同一事实结构
```

页面只在六轴齐全时填充雷达面；资料不足的轴留缺口。比较使用固定五档尺度，不生成合计或排名。旧 `criteria_version: 1` 按原来的「经验发挥／业务方向／职责与裁量／成长空间／协作适配／工作条件」显示，并明确为旧版口径；版本不同的轴不得伪装为同一维度进行对齐比较。

交付时检查选中上下文、两个及三个项目对比、来源跳转、资料不足与面谈确认事项的区分，并确认公司总览的更新没有改变历史准备稿或旧评价报告。说明对比的实际入口，让用户能从公司总览自行进入。
