# 公司总览与契合评价

公司画像用于了解当前公司与岗位，并以相同维度比较最多三项。六维图表达**有依据的面试前判断**：对照已读的当前求人、公开资料与本人已确认的经历和方向，不把企业内部实际情况说成完全确认。它不是录用概率、公司综合质量或应募投入优先级。程序契约以 `lib/company-overview.ts` 为准；写入后运行 `npm run vault:verify` 并回读页面。

## 资料归属与更新

- 公司卷宗 `type: company` 的可选 `company_profile` 保存业务、人数、成立、集团／上市关系与外部口碑。公司规模、薪资、知名度都不直接换算契合分。
- 公司卷宗的可选 `company_summary` 双链指向独立 `report_kind: company-summary` 报告，同公司不同岗位共享公司层面的研究。总结不塞进 `fit_assessment.summary`；后者继续表达本人和具体岗位的一句话契合判断。
- 岗位／面谈条件保存在契合报告的 `context_facts`，不写到共享公司事实。与 job-case 的当前事实冲突时先核对原文，不自动采纳旧评分卡的值。
- 每次实质重评新建 `80_AI分析/YYYY-MM-DD_Codex_<案件或面谈短名>_会社契合.md`；不要覆盖旧报告或别的作者的分析。同日已存在则增加修订后缀。
- 新评价使用 `schema_version: 1`、`criteria_version: 2`。前者是存储结构，后者是评价口径，不要同步改成 2。旧 `criteria_version: 1` 报告保留原文、分数与旧轴；不能改版本号或把旧分数映射到新轴。按新版实质重评后再更新最新引用。
- 在真实 job-case 或面谈 TODO 上写 `company_dossier` 和 `fit_assessment` 双链，指向卷宗及最新报告。报告 `case`／`meeting` 二选一，对应同一记录；不按显示公司名合并、不为显示画像伪造案件。
- 页面显示最新画像日期，与历史准备正文分开。不要改旧准备稿来加入画像，也不要增加其轮次或第六章。

## 公司总结：从资料形成整体理解

公司总览先突出岗位判断与面谈重点，用紧凑事实和契合画像帮助浏览；公司故事保留可读的开头及完整展开入口，外部评价能继续读到具体依据。显示折叠不能截断保存的研究正文。默认按 [公司与人物的故事](company-story.md) 写连贯中文长文：解释公司怎样走到今天、客户与最终使用者怎样获得价值、哪些转折带来现在的工程与组织任务，再连接当前岗位。篇幅随证据与理解需要展开，不设数百字或固定段数的摘要上限，不靠重复拉长。稳定的创办者／员工职业故事可帮助理解业务；本轮面试官身份与提问战术留在当前 prep。不要把事实卡改写成列表、公司沿革流水账或新闻标题合集。

研究时至少检查以下方向，记录实际读到的资料；没有公开信息就明示缺口，不强凑数量：

- 当前业务、客户与收入模式、规模和行业位置。人数与收入分清单体／集团、正式员工／合作人员、统计时间；公司较新时从成立起回顾，不编造三到五年的历史。
- 近三到五年有依据的业务变化，以及近期约六到十二个月的新闻、公告、产品发布、客户案例、合作、收购、组织调整或财报。逐一核对发表日与事件日，旧文章新抓取不等于新事件。
- 技术博客、技术分享、经营者文章和员工访谈。优先读与业务转向、工程瓶颈、开发方式和组织建设有关的原文。区分作者、部门、时间、观点、实验和已投入生产的实践；公司自述不能视为独立口碑。
- 当前岗位的公开要求及企业明确说明的招聘背景。岗位原文使用本人登录会话；复用已核验的 vault 证据时保留其读取日期，不冒充本轮新核实。

把资料连接成「发生了什么变化 → 带来什么业务或技术任务 → 为什么可能需要这一类人」的解释。只有企业明说，才写成确定的招聘原因；根据新闻、博客与岗位交叉推出的解释写“据此判断”“可能对应”，并说明还需要确认的事项。不得由招聘多、人员增加、融资或发布新产品就断言营收增长、盈利改善或岗位是扩招；补员、替换、储备招聘未获证实时保持未知。允许“收入增长但利润承压”“集团扩张而部门情况不明”等有层次的判断；缺少连续数据时不强判上升或下降。

关键事实和判断就近附直接链接。段落可用少量加粗与行内出处，读者应能顺着文章读下去；长链接标题、阅读范围和具体限制放到报告的「资料与边界」节。网页实际全文可读才能称已读，搜索摘要仅用于发现来源。近期变化可能推翻旧卷宗时先核对差异，保留原有证据，不偷偷改写历史。

每次实质更新新建 `80_AI分析/YYYY-MM-DD_Codex_<公司短名>_公司总结.md`，同日重名加修订后缀；新报告反向关联同一个公司卷宗，再替换卷宗的 `company_summary` 引用。日期为本次资料核对时点，覆盖期间另写；来源日期及适用范围不相同时在正文说明。报告格式：

```yaml
type: ai-report
report_kind: company-summary
schema_version: 1
assessed_on: 'YYYY-MM-DD'
ai_author: Codex
company_dossier: '[[20_求職/测试/_公司]]'
coverage_period: '<实际可核验的历史区间与近期动态截止日>'
sources:
  - label: '<来源标题与发表日／统计时点>'
    url: https://example.com/news/article
  - label: '<本轮实际使用的既有证据与核验日期>'
    wiki: '[[20_求職/测试/既有证据]]'
```

正文保留一个 `## 公司总结`，下方写连续自然段，可用 Markdown 直接链接与双链；一个 `## 资料与边界` 记录各来源的实际直链、发表／事件／统计日期、阅读日期、阅读范围与支持的结论。Web 只投影「公司总结」，来源区可展开并进入完整报告。缺失总结显示待补齐；坏引用只影响总结，不应使已有公司事实与契合画像消失。

## 事实与外部评价

每项事实保存 `id/label/value/as_of/scope/sources`。人数需区分单体／集团、员工／合作人员及统计时点；有冲突时保留口径并解释，不取全文中第一个数字。没有资料的内容明确写未披露／待确认，不推断稳定性或上市状态。

外部口碑默认结合 OpenWork 与転職会議，分别记录平台、原始量尺、评分、样本数及单位、评论时段、角色覆盖、阅读日期和实际可见范围；不同平台不合成平均分、不混加样本，也不把不同岗位的体验并成当前岗位事实。评论仅是样本，不证明公司普遍情况，无法读到正文时不从搜索摘要编造正负主题。官方员工访谈属于公司自述，不能当独立口碑。

`status` 为 `available / not_researched / no_samples / restricted`，分别代表已取得可用内容、未调查、调查后未找到可用样本、访问范围受限。受限页面若有可见评分与数量可记录，但 `limitations` 必须说明只读到的范围；不为取得口碑自动登录、投稿或付费。

### 双平台默认流程

1. **先核对法人，再读评价。** 完整准备默认调查 OpenWork 和転職会議，两站均使用本人已登录的 Chrome。各站以公司全名、官网域名和平台公司 ID 核对，不能合并同名公司、集团与子公司。已获授权的阅读直接继续；某站登录不可用时请本人接通该部分，继续另一站及其他不依赖它的研究。不要自行注册、登录、投稿或付费，也不退到游客视角代替会员全文。
2. **逐站分别记录整体统计与实际阅读。** 保存原始评分、量尺、样本数及单位、分类评论条数和读取日期。OpenWork 的 `sample_count` 默认填平台回答者人数；転職会議按页面实际显示的统计口径填写 `sample_count/sample_unit`，没有人数就不把评论条数换算成人数。`coverage` 分别写实际阅读量、角色／入社背景／在职或离职、发表日期和可见范围；同一回答者多个分类不能重复计人，无法去重就只报已读条数并说明。整体评分统计范围与实读正文日期范围分开写；两站样本可能重叠，不能相加声称独立人数。
3. **充分浏览相关正文与不同观点，精选展示。** 每站小样本可逐位读完可访问的回答者；大样本先明确选样范围，优先近期、同地区及相近职种，兼顾在职、中途入社与相反意见，记录职种、在职／离职、雇用背景与发表日期。按资料相关性决定阅读量，不因页面只展示少量摘录就只读那几条；实际读多少就写多少，抽读不能写成已读全部，也不为凑配额采用无关样本。平台 AI 总结与企业挑选的精选评论须区分，不能代替独立回答者正文。転職会議的「オープンデータQ&A」「口コミQ&A」等平台生成摘要不能当员工原话或独立样本；其链接及「根拠となった口コミ」节选可作发现线索，须打开原评论核对角色、发表日期和可读正文后，才计入完整实读。无法读到正文时只保留可见统计及访问限制，不推测正负主题。
4. **说明评价能覆盖到哪里。** 公司整体分数不等于某部门、某招聘职位或某位上司的情况。中介公司内部营业员工的体验也不等于自由职业利用者或客户工程现场的工时、报酬与支持。正文观点归于回答者；对工时、评价、经营或报酬的指摘不是已审计的全公司事实。保留相反观察及评论陈旧、样本偏斜等限制。
5. **保存证据并让页面可见。** 在公司资料目录保存有日期与作者的原文确认笔记，按平台分别用短摘要记录统计、实读元数据、回答者或评论直接 URL、正负观察和限制，不整篇转载。将 `company_profile.review_synthesis` 保存为跨平台整体解读，`company_profile.reviews` 为两站各保留一项独立平台卡与代表性主题，不能用新站替换旧站；完整填写下方字段。公司总结与当前 prep 解释这些观察怎样影响本次判断，研究资料保留正文直链。公司总结／契合评价有实质变化时新建修订报告，保留旧报告；未举行的当前 prep 沿用本轮身份。
6. **把观察变成面谈问题。** 选一至三个与实际岗位、对方身份有关的核实点，融入现有五题及接话，不另加通用问卷。用“最初怎样安排项目”“遇到职责偏差怎样协调”等开放问法，不以“网上都说”施压，不把未经核实的指摘嵌进问题前提。外部评分与六维契合判断分开，不把评分直接换成雷达分或据此作录用概率判断。

两站各自判断 `status`：`no_samples` 需要有实际调查依据；尚未查用 `not_researched`，被会员墙挡住用 `restricted`。取得公司员工样本而没有当前项目样本时，仍可用 `available`，在 `coverage/limitations` 明示缺口，不能把可用评价隐藏成“没有评价”。某站受限不抹掉另一站的有效内容，也不声称已完成双平台全文核对。双平台之外的来源可用于重要缺口或交叉核对，不要求每次遍历所有平台。

### 先给整体总结，再展示代表性证据

取得有效评论后，公司总览的「外部评价」先显示面向本人决策的连续中文故事，再显示各平台原始统计、`insights` 与摘录。读者应读出这家公司为什么值得争取、主要代价或疑虑在哪里，以及下一轮听到什么具体情况会增强或改变这个判断。不能只把摘录换词，也不能用“有好有坏、因团队而异、仍需核实”作为所有公司的共同结论。

**先立主判断，让公司之间的差别可感。** 开头就突出最有分量的信号：例如两站均为四分段且有较大样本、两站评分明显分歧、相关员工反复反映资源不足，或评论太少而主要依赖现场观察。显著的原始评分应靠前、可加粗，不能埋在尾段，也不要随即用一个泛泛的负面意见抵消。分数描述的是该平台的评价格局；未取得平台基准时，不把三分当及格线，不声称排名、百分位或评分差距的统计显著性。无总体分数就明确缺失。跨平台差异不能由想象中的算法、刷评或组织变化解释。

**用具体经历讲清机会与代价怎样发生。** 从最重要的组织特点展开，而不是按正面／负面分栏各写一段：员工能与什么样的人做什么工作、怎样获得责任和支持，或为什么任务、压力与回报失配；这些体验与当前岗位及本人已确认的能力、方向有什么关系。评论可帮助理解高分或顾虑，却不证明某主题在计算上造成了平台总分。按岗位相关性、时效、反复出现的程度和情节具体性分配篇幅，不凑正负平衡；个别但严重的沟通或职责风险应保留并归于该回答者。相反体验只有在会改变理解时才展开，说明它是可选的另一种工作方式、局部差异还是尚未解释的冲突。不要用一条好评消除重复的顾虑，也不要用一条抱怨抹掉一致的优势。

**把故事落到本人可以做出的选择。** 有吸引力的环境要讲清值得争取什么、本人的经历怎样证明能参与；资源或职责存疑时要讲清需要怎样的项目实例、分工或支持安排才值得继续。用条件性的具体判断收住，例如“若最初任务确实是共同基盘改造，便能发挥已做过的性能与正确性改善；若只剩既定报表维护，吸引力会减弱”，而不是只列待问清单。不要替本人编造偏好或作最终入社决定；评分也不替代具体岗位、契约和实际沟通。

证据范围仍须清楚，但不要让数据审计说明吞掉叙事。影响主判断的边界在相邻处简短交代，如旧部门经验、单人面试自述或中介内部营业；详尽人数／条数、抽读方法与日期放在 `coverage` 和「资料与边界」。核对部门、角色、入社背景和时期能否解释分歧；不足以解释时保留未知，不把单人意见写成共识。一站没有可读正文时，明确总结只基于另一站，不编造跨平台印证。篇幅随理解需要展开，不设固定段数或字数上限。

交付前通读正文：去掉公司名后，是否仍能原样套给另一家公司？高分、分歧或样本稀薄的特点是否进入主判断？读者是否知道下一轮要争取什么、什么回答会改变选择？若只剩“兼顾优点、留意风险、面谈确认”，应回到具体证据重写。

`company_profile.review_synthesis` 保存下列结构，至少有一段正文和一项有效来源。`coverage` 逐站明写总体样本数及单位、实际实读人数或条数、选样范围、角色及日期覆盖和主要缺口；只有确实逐人读完可访问样本才称读完。`as_of` 是本次核对日期，`ai_author` 使用具体署名；`sources` 可链接两站回答者／评论原文或已存在的原文确认笔记，不能只给搜索页。没有有效评论时不编写总结。网页折叠展示可以精简首屏，但须保留完整正文与来源入口。

```yaml
company_profile:
  review_synthesis:
    as_of: 'YYYY-MM-DD'
    ai_author: Codex
    paragraphs:
      - '<连续中文故事：主判断、评分格局、关键经历与本人选择；可用 Markdown 加粗、直接链接或有效双链>'
    coverage: '<逐站总体样本与单位、实读人数或条数、选样范围、角色／发表日期覆盖及不能推广到的范围>'
    sources:
      - label: '<已读回答者原文或确认记录>'
        url: https://example.com/review/respondent
      # 引用已存在的笔记时用 wiki: '[[唯一笔记路径]]'，与 url 二选一。
```

### 把外部评价写得具体、可追溯

`positive/negative` 是概览，不能代替正文解读。取得有效评论后，用 `insights` 按有信息量的主题说明：员工经历了什么、正反观察是否并存、为什么与本岗位有关、面谈应核实什么。优先讲具体情境，例如学习时间怎样安排、项目任务怎样变化；避免只写“成长好／工时长”。主题数量随实际证据决定，不强凑正负平衡。

每个主题的 `evidence` 记录回答者职种及在职背景、发表日期、直达原文的链接和中文转述。按与岗位的关联、反复出现的程度及能否说明分歧挑代表性证据，不把全部已读评论搬到页面；个别但重要的相反意见可保留并注明其范围。需要让本人感受原话时，选少量已经逐字核对的短摘录放入 `quote`；摘录与转述分开，不能把中文总结反译成日语冒充原文，也不整篇搬运评论。原文不完整或未实读时省略引文并注明阅读边界。平台回答者人数用 `sample_unit: 名回答者` 标清；只显示评论条数时保留该单位，不冒充人数，实际抽读数量仍写入各平台的 `coverage`。

```yaml
insights:
  - title: '<具体主题，不只给正面／负面标签>'
    kind: mixed # positive / concern / mixed
    summary: '<结合具体情境解释观察，保留相反体验与适用范围>'
    implication: '<对本岗位的意义与需要核实的事项>'
    evidence:
```

## 六维评价（criteria_version: 2）

固定顺序与含义。所有判断均以面试前可取得的证据为范围：

| key | 维度 | 证据要回答的问题 |
|---|---|---|
| technical | 技术匹配 | 求人中明确的技术需求，与本人已证明的技术基础及可迁移能力是否匹配？ |
| experience | 经验发挥 | 岗位要解决的问题、交付的成果物和承担的责任，能否发挥本人已有实绩？ |
| business | 业务方向 | 公司解决的问题是否与本人当前兴趣与方向一致？ |
| role | 职责方向 | 求人声明的角色与责任方向，是否符合本人当前志向？ |
| growth | 成长方向 | 公开的具体职责或技术学习机会，是否有助于本人希望积累的经验与能力？ |
| practical | 已知条件 | 已公布的雇用、地点、工作方式、工时，与本人已确认接受的范围是否相容？ |

- **技术匹配与经验发挥分开看**：前者看技术基础和实际差距，后者看解决问题、交付和责任经历。产品名称不完全一致不自动扣分；也不能把可迁移能力写成目标产品的生产经验。
- **业务方向**按公司实际解决的问题与本人当前方向判断，不能自行用行业、规模或知名度设偏好。
- **职责方向**评价求人所声明的角色。实际决策权、配属、第一阶段责任和是否能兑现，留到面谈确认，不把招聘文案升级为已获授权。
- **成长方向**必须落到具体技术、任务或责任积累。它不证明公司提供培训、导师、晋升或一定能配属到理想项目。
- **已知条件**只评价已公开且能与本人现行接受范围对照的条件；不表示就职手续与全部待遇已成立。薪资仍在事实卡独立展示，不能把高薪、完全远程或大公司自动换成高分，也不将本人已接受的出社、地域列成缺点。

分档：1 明确不合、2 契合较弱、3 基本适配、4 明显契合、5 高度契合。已知但好坏并存可以是 3；证据不足必须是 `null`，不能先填中间分。公司业务或岗位有多个方向时，不把其中最理想方向当已配属。5 需要直接、具体的适配证据；不能因为企业自称重视成长就打高分。

每个数值必须同时有简短判断和证据：公司／岗位来源加相关本人素材。轴本身所需的公开证据不足时用 `null`，页面显示「资料不足」，在 `rationale` 和 `unknowns` 说明缺少什么；不能为了画满雷达图补分。薪资按本人现行方针协商，不自设下限。不要读取旧 `rating/fit_score_100` 作为默认值。

**面谈才能回答的问题单独进入 `fit_assessment.questions`**：例如实际裁量、具体配属、沟通分工、初期支持、在留手续支持和条件兑现。它们仍须在主图旁可见，但不因这类内部情况尚未确认就把已有公开依据的轴置为 null。`unknowns` 用于记录该轴证据的具体限制；不要把面谈问题机械复制到每一轴。公开资料若已显示明确不适配，应如实判断，不以「面谈再问」掩盖现有反证。
