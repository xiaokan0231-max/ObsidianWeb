# job-posting-review：求人原文を読んで採点し、起票する

このスキルだけが `type: job-case` を作れる。つまり **Web 看板に載る＝ここを通った**、
という意味を保証するのが役目。探索（job-search-scan）が拾ってきたキューは「見つけただけ」で、
まだ何の評価も受けていない。

規則の正本は vault にある。ここは工序だけを固定し、規則を複製しない。

## 🔴 一次情報だけで判断する（このスキルの存在理由）

- 判断根拠にしてよいのは**求人原文の各欄の本文**だけ。検索ヒット・技術タグ・
  媒体カードの要約・同社の別ポジションは根拠にならない（`_ルール_求人探索と採点` §0）。
- **原文に到達できなければ点数を付けない。** `found_original: false` として据え置き、
  キューの行はそのまま残す。「確認できなかった」と書くのが正しい仕事。
- 外部サイトは**読むだけ**。応募・保存・気になる・メッセージ送信は一切しない。
  応募するかどうかは本人が決める。

## 工序

### 0. 正本を読む

1. `99_系统/_数据字典.md` — 字段字典と唯一 writer 表
2. `20_求職/_求人検索条件.md` — 現在の波・core技術・除外条件4つ（SEARCH-EXCL）
3. `20_求職/_AI推薦/_ルール_求人探索と採点.md` — 採点基準 (a)〜(i)、直投URL規則 §3.5、
   応募前チェックリスト §4、**失敗記録20件**
4. `10_关于我/求職硬性約束.md` — 英語基準・ギャップの扱い・職種の許容範囲

### 1. 対象を決める

**キューから進める場合**（既定）：

- `20_求職/_AI推薦/_探索キュー.md` を読む
- 各行について、対応する `job-case` / `excluded-job` ノートが既にあるかを確認する
  （`lib/job-queue.mjs` の照合規則と同じ：会社名キー＋職種名の部分一致）。
  **あるものは精読済み。ないものが対象。**
- キュー末尾の「優先順」と「先に潰すべき論点」を見て、**core技術が必須欄にある可能性が
  高い順**に取る。今回何件やるかを最初に決めて宣言する。

**URLを貼られた場合**：そのURLだけを対象にする。キューは触らない。
ただし起票前に必ず既知集合と照合する（下記2）。

**再採点モード（規則正本が変わった後・本人が明示した時だけ）**：
既定工序は job-case 既存の行を「精読済み」としてスキップするため、規則変更後の再採点は
このモードを明示的に指定して起動する。

1. どの規則が変わったかを特定し、**影響を受けるノートだけに絞る**
   （例：(a) の仕事内容欄改定 → 「core 技術が仕事内容欄にあり必須欄にない」ノートのみ）。
   影響しないノートは再採点しない——新旧規則で同点になるものを読み直すのは浪費
2. 再採点の証拠は**ノート内の逐語引用（必須要件・採点論証）を第一に使う**。
   原文を開き直すのは逐語証拠が足りない時だけ。求人が掲載終了なら
   `found_original: false` のまま点数を動かさず「新規則での再評価は原文消失により不可」と注記
3. 点を**上げる**場合は、根拠となる逐語引用の行を指せること
   （2026-07-20 再監査＝過大4件・過小0件の楽観バイアス対策。迷ったら低い方）
4. 変更したノートに再採点日と適用規則を1行残し、終わったら `npm run vault:stats`

### 2. 照合（起票前に必ず）

- `_不採用台帳_正.md` の全社照合リスト（表記ゆれ：全角/半角・「株式会社」の位置）
- `20_求職/` 配下の全 `job-case`
- `_AI推薦_除外/` の `excluded-job`

同社の別求人は**重複ではない**。ただし既存案件へリンクを張り、応募経路が衝突しないか注記する。

### 3. 原文を読む（1件ずつ）

個別求人ページを開き、**欄を分けて**逐語記録する：

| 記録する欄 | なぜ |
|---|---|
| 職種名 | 誇張しにくい＝強い証拠 |
| 仕事内容欄の**動詞と目的語** | 「パイプラインを構築する」か「予測モデルを構築する」かで職種が変わる (f-2) |
| 必須要件欄（**逐語・コードブロック**） | 要約禁止。後から誰でも検証できる状態にする |
| 歓迎欄 | core技術がここ止まりなら日常業務ではない (i) |
| 語学欄・本文中の「英語」全出現箇所 | 福利厚生欄の英語クラスは語学要件ではない（失敗#3） |
| 雇用形態・勤務地・年収 | 業務委託は除外。勤務地は原文どおり（失敗#6） |

そして **core技術がどの欄にあるかを必ず記録する**。欄が違えば意味が違う。

同社に複数求人があるのは常態。**求人の同一性は職種名＋求人IDで確認する。**
一つ読んで他を推測してはいけない——ソニーの2求人は必須要件がほぼ同一なのに
片方だけ英語必須だった（2026-07-22 実証）。

### 4. 除外判定 → 採点

まず SEARCH-EXCL 4条。**職種の中核**が該当するなら除外、
必須欄に語が混ざっているだけなら除外せず減点（4〜6点）。社内折衝・中国語折衝は加点。

除外でなければ (a)〜(i) で採点する。特に外しやすい2点：

- 必須筆頭が完全未経験 → 書類で弾かれるリスクとして、ギャップ枠とは**別に**減点 (i)
- core技術が歓迎欄・将来役割欄のみ → 日常業務ではない。加点しない (i)

### 5. 自查（採点後に必ず・楽観バイアス対策）

打った点数について、**その根拠が原文のどの行かを言えるか**を1件ずつ確認する。
言えない加点は落とす。

根拠：2026-07-20 の10件再監査で**4件が過大評価・0件が過小評価**だった。
偏りは一方向にしか出ていない。**迷ったら低い方**に倒す。

さらに次の3つは「書いてないこと」を根拠にしていないか点検する：

- 国籍・クリアランス要件を推測で足していないか（失敗#9）
- 勤務条件（24時間対応など）を求める人材像から推測していないか（失敗#20）
- 旧版求人票や別ポジションの記述を混ぜていないか（失敗#18・#14）

### 6. 起票

**応募候補** → `20_求職/_AI推薦/<会社>_<職種>.md`、`type: job-case`、`status: 未応募`。
frontmatter は既存案件（例：`SUNPIN_JAPAN_…md`）に合わせる。
`official_apply_*` は §3.5 の判定に厳格に従い、確認していないなら `unavailable` と
「未調査」と書く。採用トップで埋めない。

🔴 **本文には Web が読む4つの小節を必ず入れる。** これが無いと看板で評価が空欄になる
（正本は `lib/jobs.ts` の `jobSection(note, ...)`）。

### この4小節は**中国語・簡潔に**書く（2026-07-22 本人指示）

看板でこれを読むのは本人。長いと読まれない。

> 本人の言葉：「太啰里吧嗦了太复杂了，简约一点」「不需要为什么7分不是8分，
> 你就告诉我9分那是加分点哪些扣分点就可以了，然后给我一个理由」

**4小節あわせて 400〜600 字が上限。** 推荐理由は 150〜250 字。

やらないこと：
- ❌「为什么是7分而不是8分」式の点数の弁明
- ❌ 他候选との名指し比較（看板は並べて見えるので不要）
- ❌ 規則番号・失敗番号の引用（技術取証のほうに書く）
- ❌ 同じ内容を推荐理由と注意点で二度書く

```markdown
## 推荐理由
1〜2文で：这个分是几分、core技術在哪个欄、加分是什么、扣分是什么、结论一句。
例：「9分。必須欄明写 Hadoop／Spark，必須6项里5项直接对上，リーダークラス让管理经验算加分。
扣1分：必須最后一条 MLOps 的实操经验薄。原文没有『英語』一词。」

## 匹配点
4〜6条。**1条＝1行**（改行禁止。`lib/jobs.ts` の `jobSectionItems` は
`^- ` 始まりの単一行しか拾わないので、折り返すと Web で消える）。
形式：`- 必須「原文の短い片段」＝ 本人の実績`

## 注意点
2〜4条、各1行。ギャップ・取り違え注意・未確認事項。
**分数が動く条件が1つだけあるなら1行で書く**（例：`- 面谈确认X的话升到7分`）。

## 主打材料
3〜4条、各1行。どの書類・どの実績を前に出すか。
```

技術取証（`## 必須要件（求人原文・逐語）`・`## 採点論証`）はこれとは別に必ず残す。
**細かい論証・規則の引用・他候選との比較はそちらに書く**——Web には出ないが、
後から検証できる状態にするために要る。**逐語引用は日本語のまま**（翻訳すると証拠でなくなる）。

**除外** → `20_求職/_AI推薦_除外/<会社>_<職種>.md`、`type: excluded-job`＋
`_除外リスト.md` に一行追記（両方やって初めて完了）。除外理由が英語のみの場合は
「技術面は合致していた」と明記する——本人の英語の壁が解けた時に再評価する対象になる。

**起票しない**（掲載終了・重複掲載など）→ キューの職種名末尾に `【取下げ:理由】` を追記。
行は消さない。消すと次の探索でまた拾って往復する。

### 7. 校验

```bash
npm run vault:check && npm run vault:stats
```

`vault:stats` がキューの `queue-stats` 区块を再計算する＝残数が更新される。

### 8. 報告（固定テンプレート）

```markdown
## 精読結果 YYYY-MM-DD
- 今回：N件精読（キュー残 M件 → M-N件）
- 起票（N件）：| 会社 | 職種 | 点 | core技術がどの欄にあったか | 一行の理由 |
- 除外（N件）：会社＋該当した除外条件＋原文の該当箇所
- 取下げ（N件）：会社＋理由
- 原文に到達できず据え置き（N件）
- 9-10点「今週応募すべき」：名指しで列挙
- **どこで止めたか・なぜ止めたか**（残りを黙って切り捨てない）
```

## 完成定義（4つ全部）

1. 触れた行すべてに行き先がある（起票／除外／取下げ／据え置き）
2. 起票したノートに Web 用4小節と必須要件の逐語引用がある
3. 除外は `_除外リスト.md` にも入っている
4. `vault:check` 通過・`vault:stats` 実行済み（キュー残数が更新されている）
